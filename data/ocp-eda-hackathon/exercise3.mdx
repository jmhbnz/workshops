With the advent of generative large language models, enriching events with additional, high quality context automatically is trivial with Event Driven Ansible.

In this challenge track, your goal is to wire up alerts for a crash looping application into Event-Driven Ansible. Event Driven Ansible will be configured to retrieve some details about the application and provide this context to a model endpoint for automated analysis. The resulting enriched alert can then be routed to the right place, with the right context.

> **Background:** [Event Driven Ansible](https://www.ansible.com/use-cases/event-driven-automation) can ingest real-time events from external sources like OpenShift's Prometheus Alertmanager stack. When an alert fires, an ansible rulebook can evaluate the alert payload, and immediately run a required playbook.


## 2.1 - Deploying a workload

Your first task for the challenge is a simple one, deploy the crashlooping workload located at [crashing-workload.yaml](https://github.com/jmhbnz/workshops/tree/main/data/ocp-eda-hackathon/workload/crashing-workload.yaml).

Reviewing the yaml, you'll notice this example workload is intentionally configured to automatically crash, with some specific log messages output. Don't worry about analysing this now, we'll configure a model to provide crash analysis context later in this challenge.

Once your application pods are successfully deployed, move on to the next task.

## 2.2 - Configuring ansible credentials

When Event Driven Ansible catches a crash alert, it will launch a playbook job template in Ansible Automation Platform to gather diagnostics and invoke the model endpoint to analyse this further.

You second task for this challenge is to enable this interaction to occur securely by creating an API Token with `write` scope for Ansible Automation Platform, and then storing this as a credential within the Event Driven Ansible infrastructure configuration.

![aap-credential](/workshops/static/images/ocp-eda/aap-credential.png)


## 2.3 - Event driven ansible basics

Within Event Driven Ansible, rulebooks within source control repositories are organized into logical collections called projects. Create a project pointing to rulebooks contained in `https://github.com/jmhbnz/workshops`. 

Once your new project has `Completed` a sync successfully your task is to create a [Decision Environment](https://docs.redhat.com/en/documentation/red_hat_ansible_automation_platform/2.7/administer-assembly_eda_decision_environments). A decision environment is the container environment your rulebook will execute within.

![ecosystem-catalog](/workshops/static/images/ocp-eda/ecosystem-catalog.png)


## 2.4 - Listening for events

Now it's time to tell Event Driven Ansible to listen for incoming events from OpenShift Alertmanager. Your task is to configure `rulebook/crashloop-ai-analysis.yaml` to process incoming events on port `5000`.

![rulebook-activation-docs](/workshops/static/images/ocp-eda/rulebook-activation-docs.png)


## 2.5 - Taking action on events

With Event Driven Ansible now listening for crash events, your next task is to configure the Job Template that will execute when `KubePodCrashLooping` triggers.

For this task, configure an appropriate job template that will run the existing playbook [`acme-ai-crash-analysis.yaml`](https://raw.githubusercontent.com/jmhbnz/workshops/refs/heads/main/data/ocp-eda-hackathon/playbooks/crash-analysis.yaml).

Hint: The playbook extracts recent pod container logs from OpenShift, wraps them into a prompt query, and sends an API call to a model endpoint to analyze the failure context. Ensure the job template will have appropriate credentials to complete these tasks.
