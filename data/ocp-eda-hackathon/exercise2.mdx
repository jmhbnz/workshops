In financial services environments, zero-day vulnerabilities and unexpected runtime process executions require immediate containment to stop lateral movement across cluster networks. SecOps teams cannot afford to wait for an engineer to review an alert at 3:00 AM when an unauthorized execution occurs inside a core transaction processing workload.

In this challenge track, your goal is to wire up Red Hat Advanced Cluster Security runtime policy violations directly into Event-Driven Ansible. When Advanced Cluster Security detects a policy violation such as a rogue shell execution Event Driven Ansible will immediately trigger an Ansible Playbook to isolate the compromised pod via a quarantine `NetworkPolicy`.

> **Background:** [Event Driven Ansible](https://www.ansible.com/use-cases/event-driven-automation) can ingest real-time events from external sources like OpenShift's Prometheus Alertmanager stack. When an alert fires, an ansible rulebook can evaluate the alert payload, and immediately run a remediation playbook.

## 1.2 - Configuring ansible credentials

When Event Driven Ansible receives an event matching certain threat alert criteria we will configure it to automatically run a remediation playbook in response to isolate the workload.

You second task for this challenge is to enable this interaction to occur securely by creating an API Token with `write` scope for Ansible Automation Platform, and then storing this as a credential within the Event Driven Ansible infrastructure configuration.

## 1.3 - Event driven ansible basics

Within Event Driven Ansible, rulebooks within source control repositories are organized into logical collections called projects. Create a project pointing to rulebooks contained in `https://github.com/jmhbnz/workshops`. 

Once your new project has `Completed` a sync successfully your task is to create a [Decision Environment](https://docs.redhat.com/en/documentation/red_hat_ansible_automation_platform/2.7/administer-assembly_eda_decision_environments). A decision environment is the container environment your rulebook will execute within.

## 1.4 - Listening for events

Now it's time to tell Event Driven Ansible to listen for incoming events from Advanced Cluster Security. Your task is to configure `rulebook/acs-containment.yaml` to process incoming events on port `5000`.

## 1.5 - Taking action on events

As outlined in the challenge overview, our goal for this track is to automatically take machine speed action when a specific type of security event occurs. With our previous task complete Event Driven Ansible is already listening for these events, and as outlined in [`rulebook/acs-containment.yaml`](https://raw.githubusercontent.com/jmhbnz/workshops/refs/heads/main/rulebooks/acs-containment.yaml) we will be using the `run_job_template` action to run a playbook in response to events matching our criteria.

For this task, configure an appropriate job template that will run the existing playbook [`secops-quarantine.yaml`](https://raw.githubusercontent.com/jmhbnz/workshops/refs/heads/main/data/ocp-eda-hackathon/playbooks/secops-quarantine.yaml).

Hint: Ensure the job template is configured to enable the playbook to be able to receive variables from the incoming event, and take action within OpenShift.

![job-template-run](/workshops/static/images/ocp-eda/job-template-run.png)


## 1.6 - Sending security events

If you've made it this far great work! Your next task for this challenge is to configure Red Hat Advanced Cluster Security to send violation events to our newly created Event Driven Ansible listener.

Retrieve your Advanced Cluster Security central login credentials from their `secret` within OpenShift and set up the new webhook notifier integration within the Advanced Cluster Security web console which points to your event listener endpoint.

With this new webhook notifier integration created, assign it to the `Unauthorized Process Execution` policy within Red Hat Advanced Cluster Security.

![rhacs-integration](/workshops/static/images/ocp-eda/rhacs-integration.png)


## 1.7 - Testing the process

It's time. We can now test out the process. With the `Unauthorized Process Execution` policy set to send violation events to Event Driven Ansible your task now is to prove the process works.

Start by ensuring the [process baseline](https://docs.redhat.com/en/documentation/red_hat_advanced_cluster_security_for_kubernetes/4.11/html/operating/evaluate-security-risks#use-process-baselines_evaluate-security-risks) for your sample workload in OpenShift is `locked`.

Once the lock is set, open up a terminal within the sample workload pod, and run a process that is not part of the baseline.

![terminal-command](/workshops/static/images/ocp-eda/terminal-command.png)

If everything is wired up correctly you should see:

- A policy violation event recorded in Red Hat Advanced Cluster Security
- A job template run in Event Driven Ansible
- A `NetworkPolicy` successfully applied in OpenShift to isolate the workload

If those three things are in place, congratulations you have completed this challenge track! You're now responding to security threats at machine speed, with all of the flexibility of the Ansible ecosystem, augmenting your OpenShift application platform! 🎉
